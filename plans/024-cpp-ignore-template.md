You are Hānihi working on this Rust repository. You may edit tracked files
and make local git commits — never push. This is plan 5 of 5 — the last in a
series that makes Hānihi work well in a C++ project. This plan is
self-contained: implement it even if none of the other four exist yet, and
do not modify anything in anticipation of them.

## Objective

Fix the C/C++ ignore template so a CMake build tree is invisible to the
agent. Today the generated `.ignore` covers `CMakeFiles/` and `cmake-build-*/`
but not an in-source `CMakeCache.txt` or the rest of what a configure step
drops into a source directory, so a misconfigured repo leaks build noise into
every `list_dir` and `grep`.

This is the smallest of the five plans and the only one that changes the
on-disk `.ignore` file in every C/C++ repository Hānihi opens.

## Read first, verbatim

- `crates/hanihi-core/src/source.rs`
  - `Language` enum and `Language::template` (~28-52) — the `.ignore` text
    for each language. Read the `Language::C` arm character by character; it
    uses `\` line continuations inside a multi-line string literal, and any
    edit must preserve that form or the emitted file gains stray whitespace.
  - `HANIHI_HEADER` (~23-24) — the marker line that makes `ensure_ignore_file`
    idempotent.
  - `ensure_ignore_file` (~296-328) — **the most important function in this
    plan.** Understand exactly when it does and does not write: it prepends
    the template only when `HANIHI_HEADER` is absent, and never rewrites an
    existing file that already carries the header.
  - `detect_languages` (~330-372) — which extensions and marker files select
    `Language::C`.
  - `mod tests` — specifically `ensure_ignore_file_bootstraps_rust_template`
    and `ensure_ignore_file_preserves_user_content`, the two tests that pin
    the current behaviour, plus `testutil::Fixture`.
- `.ignore` at the repository root — the live instance of the generated
  file. Read it. If it differs from what `Language::template` would emit,
  note that before changing anything.
- `README.md` — the "Source tree access" bullet describes the template
  material ("`Cargo.toml` → Rust; CMake/Makefile/C-family sources → C/C++")
  and the `Language::C` doc comment says the same. Both may need a wording
  touch-up.

## Findings (confirmed)

1. The `Language::C` template contains `build/`, `cmake-build-*/`,
   `CMakeFiles/`, a set of object/library/executable extensions
   (`*.o`, `*.obj`, `*.a`, `*.so`, `*.dylib`, `*.exe`), coverage data
   (`*.gcda`, `*.gcno`), `a.out`, and `.cache/`.
2. It does **not** contain `CMakeCache.txt`, `CMakeUserPresets.json`, or
   `compile_commands.json` — despite the template ending with the comment
   "# compile_commands.json — sometimes committed; useful for the agent",
   which documents a decision not to ignore it. That comment must be
   preserved; it is a deliberate choice, not an oversight.
3. `ensure_ignore_file` is **header-gated**. A repository whose `.ignore`
   already has `HANIHI_HEADER` will **not** receive the new patterns. Every
   existing Hānihi-managed repo is therefore unaffected by an edit to
   `Language::template` — which is both the safety property that makes this
   change low-risk and the reason the fix will not reach repos that already
   ran Hānihi. See §D.
4. An in-source `cmake -B` would be the case that creates `CMakeCache.txt` in
   the source root. Plan 2 forbids `-B` outside `build/`, so the agent cannot
   *cause* it — but a developer can, and a repo checked out with a stale
   in-source configure is a real scenario.

## Design

### A. What to add, and what to leave alone

Add to the `Language::C` template:

- `CMakeCache.txt` — written by configure into the build root; appears
  in-source when someone runs a bare `cmake .`.
- `CMakeUserPresets.json` — local, uncommitted, machine-specific.
- `*.o.d`, `*.gcov` — gcov/dependency side outputs that the existing
  coverage entries do not cover. Add only if you can confirm the extension
  is generated by common toolchains; do not invent extensions.
- `*.ninja`, `.ninja_deps`, `.ninja_log` — a Ninja build tree in-source.
  Add if and only if you can state the toolchain that emits them.
- `Testing/` — CTest's output directory, written next to the test's working
  directory. This one is worth including because `ctest --test-dir build`
  keeps it inside `build/`, but a bare `ctest` in the source root creates it
  in the repo.

**Do not add `compile_commands.json`.** The existing comment says it is
sometimes committed and useful to the agent. Preserve that decision. If you
disagree with it, do not act on the disagreement inside this plan — raise it
in your write-up as an open question with your reasoning, and leave the file
visible. Changing it silently would make the template's own comment a lie.

**Do not add `CMakeLists.txt`-adjacent source patterns** (no `*.cpp`, `*.h`,
etc.). Ignoring source files is never correct.

Be conservative. Every pattern added to this template is applied to every
C/C++ repository Hānihi opens, and a wrong pattern hides real work from the
agent. Prefer a short list of patterns you are certain about over a long list
inhaled from a `.gitignore` collection. If a candidate pattern's provenance
is "I have seen this", leave it out and list it in your write-up.

### B. Keep the template a constant

`Language::template` returns `&'static str` and must keep doing so — it is
called on every `SourceTree::open_at`, and its output is written into a file
that the ignore matcher is then built from.

Preserve the existing formatting idiom exactly: the `\` line-continuation
style with the trailing `\n` on each pattern group, and the trailing comment
line. Follow the surrounding code's alignment. Do not reformat the Rust or
the C arm; `cargo fmt` does not touch string literal contents, so the file's
current shape is the author's intent.

Add the new patterns to the existing group rather than appending a new
section, unless a new section is genuinely clearer — if you add one, give it
a short `#` comment in the same style as the existing
`# compile_commands.json — sometimes committed; useful for the agent` line.

### C. Update the doc comment and the README

- `Language::C`'s doc comment says "C or C++ — detected by
  `CMakeLists.txt`/`Makefile`/C-family sources." That stays accurate.
- `README.md`'s "Source tree access" bullet lists the detected languages.
  It does not enumerate patterns, so it likely needs no change — **verify**
  rather than assume, and only edit it if it names patterns that changed.
- Do not restate the pattern list in a doc comment. The template is the
  single source of truth; a second copy in prose will drift.

### D. The existing-repo problem — document, do not solve

Because `ensure_ignore_file` is header-gated, this change reaches only
repositories that have never been opened by Hānihi, or whose `.ignore` lacks
the header. Every repo already carrying `HANIHI_HEADER` keeps its current
patterns forever.

**Do not change that behaviour in this plan.** Making the template
retroactive means either appending new patterns to a file that already has
the header (a write to a user-visible file on every open, and a file that
grows without bound across versions) or versioning the header and rewriting.
Both are real design questions with their own risks, and neither is needed to
fix the template.

Instead, **document the limitation**:

- In `Language::template`'s doc comment or `ensure_ignore_file`'s, state
  plainly that the template is applied once, at first open, and is not
  retroactive. If the code does not already say this, adding that one
  sentence is the right change.
- Raise the retroactive-template question in your write-up as an open
  question, with the two options above and their tradeoffs, so the user can
  decide.

This is the honest outcome: the fix is correct for new repos and inert for
existing ones, and the plan says so rather than implying it fixed everything.
If you judge that inertness unacceptable, **stop and report** rather than
inventing a migration in this plan.

### E. Do not touch the Rust template

`Language::Rust` stays exactly as it is (`target/`, `**/*.rs.bk`). This plan
is scoped to the C/C++ template.

## Work order, test-first

Write the failing tests first, then implement A-C, then run the gates.

### New tests in `source.rs` `mod tests`

Follow the existing pattern — build a fixture, call `tree()`, read back
`.ignore`, assert on content. `testutil::Fixture` writes a `Cargo.toml`, so
it selects `Language::Rust` and is the wrong fixture for these tests. Add a
local helper that creates a repo containing a C-family source file (e.g.
`main.cpp`) so `detect_languages` selects `Language::C`:

```rust
/// A git repo whose contents select the C/C++ ignore template.
fn cpp_repo() -> PathBuf
```

using the same temp-dir + `uuid` pattern and cleaning up as the existing
tests do.

Tests:

1. `cpp_template_covers_the_cmake_build_tree` — assert the emitted `.ignore`
   contains `CMakeFiles/`, `build/`, and `cmake-build-*/`. The first two
   already pass today; including them makes the test state the full
   contract rather than only the delta, so a future edit that drops one
   fails here.
2. `cpp_template_covers_an_in_source_configure` — assert it contains
   `CMakeCache.txt` and `Testing/`. **This is the regression test for the
   reported gap and it must fail before your edit.** Run it, confirm the
   failure, then implement A.
3. `cpp_template_keeps_compile_commands_visible` — assert the emitted
   `.ignore` does **not** contain a pattern for `compile_commands.json`,
   and that the explanatory comment line is present. This pins the
   deliberate decision found in §A so a future "cleanup" cannot silently
   reverse it.
4. `cpp_template_has_no_source_patterns` — assert it contains no pattern
   matching `*.cpp`, `*.h`, `*.hpp`, `*.cc`, or `*.cxx`. Ignoring source
   files would be catastrophic and silent; this is a cheap guard.
5. `cpp_template_is_stable_across_opens` — open the same repo twice and
   assert the `.ignore` content is byte-identical, mirroring the existing
   `ensure_ignore_file_preserves_user_content` idempotence assertion but for
   the C/C++ path. If your edit accidentally introduces a pattern without a
   terminating `\n`, the file grows on the second open and this catches it.
6. `cpp_template_preserves_user_patterns` — pre-write a `.ignore` containing
   `vendor/` in a `cpp_repo()`, open the tree, and assert `vendor/` survives
   alongside the header and the new patterns. The C/C++ path must have the
   same preservation property the Rust path already tests.
7. `template_is_not_retroactive_for_an_existing_ignore` — a `cpp_repo()`
   whose `.ignore` already contains `HANIHI_HEADER` is left untouched, and
   specifically does **not** gain `CMakeCache.txt`. This test documents §D's
   behaviour as intentional. If you believe the behaviour is wrong, this is
   the test to change — in a different plan, with the user's agreement.
8. `rust_template_is_unchanged` — open a `testutil::Fixture` (Rust) and
   assert the emitted `.ignore` contains `target/` and `**/*.rs.bk` and
   contains no CMake pattern. Guards against a copy-paste edit landing in the
   wrong arm.

### An end-to-end sanity check

The unit tests assert on the template text. Add nothing further unless it is
cheap, but do perform this check by hand and report the result: in a scratch
CMake repo (a) open it with Hānihi, (b) run `cmake -B build`, (c) run
`list_dir` with `depth: 2` or the equivalent `SourceTree::walk`, and confirm
`build/` and its contents do not appear. If they do, the matcher is not
reading the freshly written `.ignore` and that is a real bug worth reporting
— `open_at` deliberately calls `ensure_ignore_file` *before* `build_matcher`
for this reason, so a failure here would contradict that design.

## Acceptance criteria

- The generated C/C++ `.ignore` template covers `CMakeCache.txt` and
  `Testing/` in addition to the existing CMake patterns, plus any additions
  you could justify from §A.
- `compile_commands.json` remains **unignored**, with its comment intact.
- No source-file pattern is ignored.
- The Rust template is byte-for-byte unchanged.
- The template is still a `&'static str` returned by `Language::template`,
  and still emitted by `ensure_ignore_file` exactly once per repo.
- Test 2 was confirmed failing before the implementation.
- The non-retroactive behaviour is documented in code and raised as an open
  question in the write-up.
- No new dependencies.

## Out of scope

- Making the template retroactive for repos that already have the header —
  see §D. Raise it; do not implement it.
- An `add_ignore` tool or a `--regenerate-ignore` flag (already listed in
  the README's Known TODOs) that would let the agent grow `.ignore` from
  within a session.
- Detecting the language via `CMakeLists.txt` differently, or adding a
  distinct `Language::Cpp` variant. The C/C++ merge is existing behaviour
  and plans 1-4 do not depend on splitting it.
- The `Toolchain` enum — plan 1. This plan deliberately does not use it;
  the ignore template is chosen by *language*, the command allowlist by
  *toolchain*, and those are separate questions. Do not couple them.
- Adding `cmake`/compiler commands — plan 2.
- Any change to `.gitignore` (respected, never written) or to `build_matcher`.

## Assumptions and risks

- **Every pattern is applied to every C/C++ repo.** A wrong pattern hides
  real files. The bespoke test list and the deliberate conservatism in §A are
  the mitigation. When in doubt, leave a pattern out.
- **The change is inert for existing repos.** This is the headline caveat.
  Do not report this plan as "fixed build noise in C++ repos" without
  qualifying it: it fixes the template, and the template is applied once.
- **`Testing/` has a mild false-positive risk.** A project could legitimately
  track a directory named `Testing`. It is a low-probability name for source
  code, and the CTest convention is well established; if you judge the risk
  too high, drop it and say why.
- **The template's own comment is a decision record.** The
  `compile_commands.json` comment explains why a file is *not* ignored.
  Treat the comment as the specification, not as stale prose.
- **Ordering within the series.** This plan is last because it is the least
  load-bearing: plans 2-4 do not depend on it, and it is the only one that
  performs a write into the user's repository on first open. Landing it alone
  is safe and useful.
